# FN软仓 三方源搭建完全指南

---

## 一、 项目结构（客户端、服务端）

FN软仓项目包含docker服务端和fpk客户端：
*   **服务端**：具有公告与轮播图管理、应用上传、应用编辑/管理、应用及设备信息统计、三方源聚合管理、IP限速、fpk的github直链加速、开发者系统、消息推送等功能，支持全托管模式以作为fpk应用分发平台，也支持半托管模式为客户端提供fpk下载链接。最大优点在于——任何人拿到docker镜像就可以另起炉灶构建个人专属的fpk应用分发平台。

*   **客户端**：具有公告和轮播图接收、应用列表显示、应用安装/卸载/更新/修复/配置备份与恢复、应用评分、应用收藏、开发者星球、主题跟随与设置、客户端新版本检测等功能。

搭建三方源，本质上就是搭建一个供客户端去访问的**“源地址”**。

---

## 二、 服务端玩法（Docker 部署）

**适用人群**：拥有 VPS 或公网 IP 的玩家，或者直接把 Docker 跑在飞牛 NAS 上的极客。
**核心优势**：拥有完整的网页管理后台、防刷限速、数据统计以及开发者入驻审核系统。

### 基础部署步骤
新建 `docker-compose.yml` 并启动容器（`docker compose up -d`）：
```yaml
version: '3'
services:
  app:
    image: ccr.ccs.tencentyun.com/hhxs2025/fn-appstores-server:2.10.0
    container_name: fn-appstores-server-go
    restart: unless-stopped
    ports:
      - "[::]:5660:5660"
    volumes:
      - ./data:/app/data
    environment:
      - TZ=Asia/Shanghai
      - BASE_URL=http://你的IP或域名:5660
      - ADMIN_PASSWORD=你的后台密码
```
部署后访问 `http://你的IP:5660/admin` 即可进入后台。

服务端玩法分为 **全托管** 与 **半托管** 两种模式：

### A. 全托管模式
*   **操作**：在后台「应用上传」拖入 `.fpk`，保持“托管 FPK”和“托管图标”全部勾选。
*   **逻辑**：你的服务端包揽了 JSON、图标、FPK 文件的所有存储和分发。
*   **优缺点**：极度省心，但**极度消耗服务器带宽**。如果是跑在家庭 NAS 上（通常上行带宽极低），用户下载一个 100MB 的应用会把你的宽带瞬间打满，体验极差。**仅推荐公网高带宽服务器使用**。

### B. 半托管模式（强烈推荐）
*   **操作**：在后台「应用上传」拖入 `.fpk`，**取消勾选「托管 FPK」**，保留「托管图标」，并填入 GitHub/Gitee 的外链地址。
*   **逻辑**：服务端只做“导购员”，用户下载时，服务端返回 `302` 跳转，让用户的 NAS 直接去 GitHub 下载大文件。
*   **带宽消耗真相**：虽然服务端依然会消耗一点带宽去下发 `JSON` 和 `图标`（约 20KB-50KB/个），但这点流量极小，1Mbps 的小水管也能在 2 秒内加载完一屏。**几十上百兆的 FPK 下载流量完全绕过了你的服务器。**
*   **神级实战**：对于无公网 IP 的家庭 NAS 玩家，直接配合 **52frp 的 1 元/月穿透节点**。穿透节点只负责传微小的 JSON 和图标，毫不卡顿。用户下载大文件直接走 GitHub，完美避开了家宽和穿透流量的双重瓶颈。

### C. 聚合申请（加入大源）
当你辛辛苦苦搭好了独立服务端，虽然用户可以手动添加你的地址，但**怎么让海量用户在不添加源的情况下，直接在官方源里看到你的应用呢？**
*   **玩法**：FN软仓官方源支持“树状聚合”。你可以提交你的**服务端地址**（如 `http://你的IP:5660`）进行**聚合申请**，也可以向其他跑FN软仓服务端的三方源申请聚合【不建议彼此聚合（A聚合B，B聚合A）和超2重聚合（A聚合B，B聚合C，C聚合D……）】

【FN软仓客户端-设置里面有官方源聚合申请通道】

*   **效果**：官方源或三方源源主审核通过后，你的服务端就会被作为一个“三方源”接入到它的后台了。用户打开软仓，哪怕没有添加你的源，也能直接刷到你提供的应用，获得巨大的曝光量。

## 三、 纯静态玩法（零成本、无服务器）

**适用人群**：只有几个自己开发的应用，不想碰 Docker，只想白嫖代码托管平台。
**核心优势**：零成本、零运维。

### 操作步骤：
1. 把 `.fpk` 文件上传到 GitHub Releases，获取直链。
2. 编写 `fnrc.json`，把直链填入 `download_url`。
3. 把 `fnrc.json` 托管到国内直连的静态空间。

### ⚠️ 致命避坑警告
*   **千万不要把 `fnrc.json` 放在 GitHub 上！** 因为客户端请求该文件时不走加速，国内极易因为 `raw.githubusercontent.com` 被 DNS 污染导致拉取失败。**必须放在 Gitee**。
*   **`.fpk` 文件可以放心放 GitHub**，因为客户端下载 FPK 时会自动走内置的外链加速器。

*示例 `fnrc.json`：*
```json
{
  "source_name": "我的静态源",
  "apps": [
    {
      "id": "myapp",
      "name": "测试应用",
      "version": "1.0.0",
      "download_url": "https://github.com/xxx/releases/download/v1.0.0/app.fpk",
      "platform": "x86"
    }
  ]
}
```

### 纯静态的聚合申请
即使是纯静态源，一样可以申请聚合！
你只需要在官方社区的**聚合申请表单**中，填入你的 `fnrc.json` 的 **Gitee 直链**（如 `https://gitee.com/xx/yy/raw/master/fnrc.json`）。官方服务端会自动解析你的 JSON，并把你的应用无缝合并到官方列表中。

## 四、 开发者系统玩法（多人协作）

**注意：开发者系统的所有核心逻辑都在“服务端”，客户端完全无感知。**

当你搭建好 Docker 服务端后，你不仅是源主，还拥有了一个“应用提交审核平台”。你可以邀请其他开发者入驻，实现多人协作。

### 协作流程：
1. **开发者申请**：把你的 `http://你的域名:5660/dev/apply` 发给其他开发者，对方在网页填写入驻信息。
2. **源主发号**：你在后台「开发者管理」点击通过，系统会生成一个带 `token` 的专属后台链接，发给对方。
3. **开发者提交**：开发者在他的后台页面拖入 `.fpk`，填入他的 GitHub 外链，点击保存。
4. **源主终审**：你在后台「审核中心」点击通过。服务端会自动把该应用写入 JSON 并上线。
5. **客户端展示**：用户刷新软仓客户端，只需拉取你服务端的 `/api/apps` 接口，就能看到该开发者的应用。用户完全不需要知道这是哪个开发者传的。

*💡 穿透环境提示：即使你的服务端是 1 块钱的内网穿透，开发者系统依然能完美运行。因为开发者在线填表、拖入解析、你点击审核，传输的全程只是几十 KB 的文本，毫无压力。*
